## Summary

**Verdict: NOT CONVERGED. Overall risk: HIGH.**

The 43-plan program is unusually disciplined about evidence provenance, proposed-only ADRs, deterministic spikes, negative tests, and human authority boundaries. The gap-closure sequence also maps most previously verified CR/WR defects to concrete repairs. However, six current design gaps remain serious enough to block execution: the toolchain verifier runs after Python startup hooks, authority decisions are not durably handed from Plan 30 to Plan 31, SPK-G executes third-party code without an OS sandbox, crash recovery does not guard every canonical reader, the ASVS review is not a real ASVS 5.0 L1 control assessment, and human-authored terminal artifacts are not validated after creation.

This was a read-only source review. I did not run the full suite because an existing evidence test writes the canonical validation report directly ([test_evidence.py:94](/workspace/projects/learn-napplets/tests/phase1/test_evidence.py:94)), which would violate the requested review-only boundary.

## Concerns

### HIGH

- **Plan 29 verifies the Python environment too late.** The wrapper starts the environment’s Python normally and performs verification from inside that interpreter ([tools/phase1-python:18](/workspace/projects/learn-napplets/tools/phase1-python:18), [01-29-PLAN.md:116](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-29-PLAN.md:116)). Python processes executable `.pth` lines and customization modules during `site` initialization; `-S` is what suppresses that startup path ([Python `site` documentation](https://docs.python.org/3.14/library/site.html), [Python `-S` option](https://docs.python.org/3.14/using/cmdline.html)). Malicious or unowned startup code could therefore run before the verifier. This is a boundary defect, not evidence of a current compromise.

- **Plans 30 and 31 lack a durable, correctly cardinalized authority handoff.** Plan 30 modifies no files yet requires six role decisions per intake scope ([01-30-PLAN.md:7](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-30-PLAN.md:7), [01-30-PLAN.md:57](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-30-PLAN.md:57)). Plan 31 then consumes a conversational “reviewer response” and models exactly six determinations total ([01-31-PLAN.md:77](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-31-PLAN.md:77)). That cannot represent six decisions for each candidate/scope, nor can it be replayed or digest-bound.

- **Plan 36’s “isolated directory” is not a security sandbox.** It disables package scripts and permits only a package-root import, but imported JavaScript can still execute top-level code with the worker’s filesystem, network, environment, and process authority ([01-36-PLAN.md:69](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-36-PLAN.md:69), [SPK-G recipe:96](/workspace/projects/learn-napplets/.planning/spikes/spk-g-package-conformance/recipe.md:96)). This does not satisfy the claimed least-authority boundary.

- **Plan 42 does not guard every canonical reader.** It adds recovery to `validate-research.py` routes, but `validate-planning.py` directly reads canonical source, claim, governance, security, and handoff files ([tools/validate-planning.py:105](/workspace/projects/learn-napplets/tools/validate-planning.py:105), [tools/validate-planning.py:171](/workspace/projects/learn-napplets/tools/validate-planning.py:171)). Standalone preflight or completion validation can therefore consume a prepared or mixed generation despite Plan 42’s “before any reader” truth ([01-42-PLAN.md:15](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-42-PLAN.md:15)).

- **Plan 39 does not establish ASVS 5.0 L1 coverage.** It pins only the introductory ASVS document and maps CR/WR findings without ASVS requirement IDs or an applicability matrix ([01-39-PLAN.md:65](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-39-PLAN.md:65)). The existing research uses outdated chapter labels—such as “V6 Cryptography”—while ASVS 5.0 V6 is Authentication ([01-RESEARCH.md:552](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-RESEARCH.md:552), [official ASVS V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)). The selected release tag and commit are legitimate ([official ASVS 5.0.0 release](https://github.com/OWASP/ASVS/releases/tag/v5.0.0_release)); the problem is incomplete control mapping.

- **Human-authored security and terminal results are not validated after creation.** Plan 39’s checkpoint authors `01-SECURITY.md`, but its automated verification only reruns fixture tests ([01-39-PLAN.md:90](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-39-PLAN.md:90)). Plan 40’s checkpoint can create `01-REVERIFICATION.md` and update `STATE.md` and `ROADMAP.md`, but its verification checks only the candidate dossier and preflight—not those newly written canonical artifacts ([01-40-PLAN.md:106](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-40-PLAN.md:106)). This leaves the most authoritative state transition enforced only by prose.

### MEDIUM

- **Plan 40 contradicts locked D-26 semantics.** D-26 allows a Phase 1 pass with impact-scoped blockers when a safe fallback/defer path is approved ([01-CONTEXT.md:47](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-CONTEXT.md:47)). Plan 40 instead makes any missing compatibility dimension force a blocked phase ([01-40-PLAN.md:83](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-40-PLAN.md:83)). That may be a desired stricter policy, but it must be an explicit context/requirement change, not an implementation-side reinterpretation.

- **Plan 29 changes the requirements lock without owning all bound artifacts.** Its file list omits the environment manifest and approval addendum, although the current manifest binds the requirements digest and top-level pins ([01-29-PLAN.md:7](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-29-PLAN.md:7), [toolchain-environment.json:29](/workspace/projects/learn-napplets/.planning/spikes/_shared/toolchain-environment.json:29)). The current approval also explicitly describes installing only the three top-level pins ([toolchain-approval.yaml:89](/workspace/projects/learn-napplets/.planning/research/toolchain-approval.yaml:89)).

- **Plan 41’s live acquisition mechanism is underspecified.** It requires registry metadata, redirects, integrity, provenance, and license evidence, but owns no collector or immutable response receipt and verifies primarily through fixture tests ([01-41-PLAN.md:53](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-41-PLAN.md:53)). Exact request method, host/redirect policy, response-size cap, timeout, and response-byte digest should be specified.

- **The current convergence artifact is not execution-ready.** It names all 43 plans but has no per-plan hash manifest or reviewed commit and still records `NOT CONVERGED` with current HIGH findings ([01-REVIEWS.md:1](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-REVIEWS.md:1), [01-REVIEWS.md:60](/workspace/projects/learn-napplets/.planning/phases/01-research-and-truth-baseline/01-REVIEWS.md:60)). Plan 29 correctly blocks on this, but marking it `autonomous: true` is misleading because a fresh independent review is an external precondition.
