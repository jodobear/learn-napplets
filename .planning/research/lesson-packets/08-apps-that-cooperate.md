# Lesson Research Packet — Apps That Cooperate

- **Lesson ID:** LES-008
- **Primary audience:** General web/application developers, runtime implementers, and developers exploring composition.
- **Prerequisites:** LES-005 and LES-006; understand the difference between a proposed mediated request and an observed runtime behavior.
- **Last researched:** 2026-07-24

## Learner question

What can “apps that cooperate” mean as a design question when no immutable source or observed host-mediated sibling-composition behavior supports a settled interoperability lesson?

## Intended outcome

Learners can separate a conceptual cooperation model from an observed implementation result, locate the canonical records that block archetype, convention, handler, and discovery assertions, and describe the evidence required before a real composition exercise is selected.

## Current terminology

- **Cooperation** is a project learning label for questions about focused applications, host mediation, and app-to-app conventions; it is not a declared interoperability protocol.
- **Host-mediated sibling composition** is an implementation-observation category, not a current fact: no selected host profile or observed sibling composition result exists in the canonical records.
- **Archetype**, **convention**, **registry**, and **projection** are blocked candidate taxonomy terms in `ARC-CANDIDATE-001`, not current behavior labels.
- **Handler** and **catalog** are unresolved terminology; this packet does not define replacement, routing, or delegation semantics.

## Misconceptions to address

- Two focused application cards in a diagram do not establish that they can discover, launch, replace, route to, or compose with one another.
- A candidate archetype or convention is not an interoperable application contract.
- An observed future host behavior would be implementation evidence, not automatically an upstream requirement or general runtime guarantee.
