# Lesson Research Packet — Evolving the Protocol

- **Lesson ID:** LES-013
- **Primary audience:** Protocol contributors, runtime implementers, and developers deciding where a missing behavior belongs.
- **Prerequisites:** LES-002, LES-008, and LES-012; understand that proposals, archive questions, local observations, and project policy have different authority.
- **Last researched:** 2026-07-24

## Learner question

Where should a missing behavior be researched or proposed when current protocol, registry, intent, runtime, and current-work evidence remains unresolved?

## Intended outcome

Learners can route a question to protocol, SDK, runtime, application, content, or evidence-refresh work without claiming that the route proves a venue, behavior, or accepted contribution. They can use dated open questions to preserve uncertainty and next steps.

## Current terminology

- **Contribution router** is a proposed research instrument, not an official governance process or submission workflow.
- **Protocol**, **SDK**, **runtime**, **application**, and **content** are contribution seams to investigate; their boundary is not settled by this packet.
- **Open question** is a dated, impact-scoped record that identifies work and review criteria; it is not a decision, accepted ADR, or protocol proposal.
- **Source freshness** is a review trigger, not permission to silently replace a claim, record, approval, or upstream fact.

## Implementation and runtime evidence

No protocol contribution, issue, PR, discussion, runtime implementation, or external action was performed. Current-work candidate metadata is directional only and has no immutable upstream revision. A source refresh can create targeted review work while retaining the prior record; it cannot auto-change a claim, ADR, approval, or instruction. The contribution router therefore remains a deterministic scenario exercise that records source state and routes research, not a live contribution client.

## Drift and open questions

- `DRF-DISCOVERY-001`, `DRF-METADATA-001`, and `DRF-INTENT-001` remain **blocked**: discovery, registry/projection metadata, and handler/catalog assumptions have no immutable released/current-work baseline.
- `OQ-UPSTREAM-BASELINE-001` is the dated map for official source collection, comparison, conflict handling, and required review before any claim becomes verified.
- Unpinned proposals, archive statements, issue/PR/discussion signals, and observed implementation behavior remain directional evidence or separate records; none becomes a current upstream fact by routing it.

## Misconceptions to address

- A contribution category is not a proof of the correct upstream venue, ownership, or accepted behavior.
- A draft, issue, PR, discussion, or archive reference can trigger research but cannot independently establish shipped protocol behavior.
- A source refresh does not silently settle a dispute or accept an ADR.

## Story representation

**Conceptual simulation:** A learner receives a missing-behavior card and sorts it into `source acquisition`, `protocol question`, `runtime observation`, `application design`, or `content policy`. The resulting transcript says `route for research`, names its open-question ID, and performs no network lookup, issue creation, pull request, discussion, publication, or credential action.

## System representation

**Conceptual simulation:** `missing behavior → evidence classification → dated open question → human review → possible future contribution seam`. The route deliberately omits an accepted proposal, protocol authority, repository target, publish action, or automatic claim update.

## Wire representation

No current contribution envelope, proposal schema, issue payload, registry record, handler message, or protocol amendment is validated. Use a static route table tied to canonical drift and open-question records, not a plausible submission API.

## Code representation

No SDK, runtime, protocol implementation, repository client, issue/PR client, credential, signer, package, or network example belongs in this packet. A non-executable data record may contain `question`, `evidence state`, `research route`, and `review required`, but it cannot create external state or imply an official contribution procedure.

## Candidate instrument

- **Conceptual simulation:** Contribution Router and Protocol Design Clinic with deterministic question cards, a dated route transcript, and a static table.
- **Provenance:** conceptual simulation; neither a protocol process, official governance tool, SDK/runtime implementation, nor external contribution action.
- **Safety boundary:** no network access, issue/PR/discussion creation, repository write, package action, signer, key, credential, deployment, publication, or browser run.

## Required fixtures and tests

- Derive future route cards, source-state badges, and transcript rows from common structured drift/open-question records so human and machine outputs preserve the same essential facts.
- Provide keyboard operation, reduced-motion equivalence, state inspection, reset/replay, and a static table for any later router interaction.
- Test that a route identifies evidence class and review requirements, retains the dated open question, and never reports a proposal, ADR, or upstream behavior as accepted.
